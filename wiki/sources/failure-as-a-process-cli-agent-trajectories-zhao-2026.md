# Failure as a Process: An Anatomy of CLI Coding Agent Trajectories

**Xiangxin Zhao\*, Han Li\*, Shuaiting Li, Tianyi Zhao, Earl T. Barr, Federica Sarro, He Ye†** (University College London; Nanjing University; \*equal contribution, †corresponding) — [arXiv:2607.09510](https://arxiv.org/abs/2607.09510), v1, 10 Jul 2026 (cs.SE). No venue listed; dataset released on GitHub.

## Summary

Existing failure studies treat agent failure as a final outcome. This paper's contribution is to treat it as a **temporal process**, decomposing every failed run into three annotated timestamps rather than one error marker: **t_err** (the decisive error — the error that determines eventual failure, labeled retrospectively over the full trajectory, and *not necessarily the first error to appear*); **t_lock** (the point after which the trajectory is empirically unrecoverable, with no subsequent correct recovery observed); and **t_obs** (the first observable sign of error, if any). Notably t_obs need not follow t_lock — external signals can surface before the run is doomed.

The dataset: 3,843 raw completed trajectories from **seven frontier models** (Claude Sonnet 4, GPT-5, Gemini 2.5 Pro, Qwen3 Coder 480B, DeepSeek V3.2, Kimi K2 Instruct, Devstral 2) across **three coding-agent scaffolds** (OpenHands, MiniSWE, Terminus2) on [[terminal-bench]], collected from May 2025 onward. 71.4% reuses publicly released Terminal-Bench trajectories from prior work; 28.6% was generated by the authors via Harbor under the same protocol. To enable fair cross-system comparison the authors keep only tasks where all 21 model×scaffold cells are present — 89 tasks × 21 = 1,869, minus 75 unavailable runs = **1,794 valid trajectories** (610 successful, 1,184 failed), **over 63,000 execution steps**. Annotation is LLM-assisted and human-adjudicated: Claude Opus 4.6 drafts structured annotations with evidence, then two independent human annotators verify and finalize every label. Inter-annotator Cohen's κ ranges 0.78–0.94; all final labels are human-determined. 14 findings across four research questions.

The headline result: agent failures are **predominantly epistemic** — the agent misuses information it already has, rather than lacking the capability to solve the task. Failures **begin very early** (median decisive error at step 7 of a median-27-step run), the recovery window is **short** (median one step), and the failure stays **invisible for roughly 10 more steps**, so the run is already doomed while still looking healthy. The practical implication the authors draw is that reliability work must move to earlier validation and mid-trajectory intervention rather than relying on final-outcome evaluation.

## Key points

**RQ1 — Timing (across 1,184 failed trajectories)**

- Failed runs contain a median of **27 execution steps** (mean 42), but the median decisive error occurs at step **7** (mean 11.92) — within the first quarter of the trajectory.
- **Median recovery window (t_lock − t_err) is one execution step.** 60.9% of decisive errors leave at least one recovery step, 43.9% leave three or more, and 239 trajectories stay recoverable for over ten steps.
- Median first observable failure **t_obs ≈ step 16** — about ten steps after the median decisive error. "Analyses based solely on observable outcomes can misidentify when a trajectory truly begins to fail."
- A prefix-only monitor recognizes failure well in hindsight (**82% precision** on locked-in runs) but has no foresight: median lead time relative to t_lock is **zero**, only **3.7–8.7%** of failures are flagged before lock-in, and best real-time recall is **28.8%**. Supplying the monitor with the task's requirements lifts recall from **18.2% → 28.8%**.

**RQ2 — Root cause taxonomy (Table II, 1,184 failed trajectories; 3 categories, 9 types)**

| Category | Type | Share |
|---|---|---|
| **Epistemic (57.9%)** | False premise — acts on an unverified assumption about task or environment | **30.7%** |
| | Specification neglect — ignores/forgets an explicitly stated requirement | 14.9% |
| | Output misreading — misinterprets command output or error message | 4.4% |
| | Ignored signal — continues despite contradicting evidence | 4.1% |
| | Premature action — acts before basic verification | 3.7% |
| **Competence (32.8%)** | Knowledge gap — lacks required domain/tool/API knowledge | 24.0% |
| | Capability limitation — reasonable strategy, executed wrongly | 8.8% |
| **Environment (9.4%)** | Environment blocker | 8.8% |
| | Other | 0.6% |

- Epistemic triggers are defined as cases where the information needed to avoid the error **was already available** but was ignored, forgotten, or misinterpreted. So the dominant failure mode "is not producing incorrect commands, but committing to incorrect beliefs."
- Illustrative case: agent sees `sudo: not found`, infers "I lack permission" instead of "sudo isn't installed", and every subsequent step is internally consistent but built on the false premise.

**RQ3 — Recovery (Table III: dominant behavior after recovery is empirically impossible)**

| Behavior | Share | % of wasted execution | Median tail |
|---|---|---|---|
| Gives up immediately | 18% | 4% | 2 steps |
| Repairs the wrong problem | 24% | **39%** | 21 steps |
| Keeps repeating the same approach | 15% | 29% | 17 steps |
| Performs checks that cannot change the outcome | 28% | 15% | 9 steps |
| Claims success by fabricating evidence | 15% | 13% | 8 steps |

- Only **18%** of failed runs terminate promptly; **82%** keep executing with no path to success. "Repairs the wrong problem" is only 24% of runs but **39% of all wasted execution** — the most costly behavior.
- **71% of *successful* trajectories recover from at least one error**; only 29% run clean. Making an error is not what separates success from failure — recovering is.
- Successful recoveries are much shorter: median **5 vs. 12** execution steps.
- Successful and failed runs receive observable error signals at similar rates (**74% vs. 72%**), but before lock-in **92% of successful** trajectories respond to at least one signal vs. only **37% of failed** ones. Recovery depends on acting on the signal, not on the signal existing.
- **Fabricated success appears in 26% of failed trajectories** and is a *consequence* of failure, not a cause: **84% of fabrication begins at or after the lock-in step**, and its median onset falls exactly on that step. It co-occurs with other unproductive behaviors in 41% of runs where it appears. A late-trajectory claimed success cannot be trusted on its face.

**RQ4 — Model × scaffold (21 systems)**

- Pass rates span **19% to 45%**. Under Terminus2 they range 29% (Qwen) to 43% (DeepSeek); GPT-5 goes 34% (MiniSWE) → 45% (OpenHands) → 39% (Terminus2). Gemini ranges 19% (MiniSWE) → 40% (Terminus2). End-to-end effectiveness depends jointly on model *and* scaffold, not either alone.
- Epistemic dominance is robust: epistemic share of failures ranges **44%** (Qwen3 under OpenHands) to **80%** (Claude under Terminus2), and is the largest category in **every one of the 21 systems**.

## Concepts & entities

- [[agent-evaluation]] — the paper's core methodological argument: outcome-only scoring is blind to when and why a run went wrong, and observable signals lag the actual onset by ~10 steps.
- [[terminal-bench]] — the evaluation environment; the analysis grid is 89 fully-covered tasks × 21 model-scaffold systems.
- [[harness-vs-model-attribution]] — Finding 13 is a direct data point: pass rates move substantially both across models within a scaffold and across scaffolds within a model, so neither component alone explains outcomes.
- [[agentic-harness-engineering]] — the three scaffolds (OpenHands, MiniSWE, Terminus2) are harnesses, and Finding 14 says the dominant failure cause is invariant to which one you use.
- [[code-as-harness]] — the failure anatomy is a diagnostic input for harness design: early assumption validation, recovery-length caps, lock-in detection to stop wasted execution.
- [[verifier]] — the prefix monitor experiment quantifies how weak real-time verification currently is (82% precision but ~zero lead time, 28.8% best recall), and shows task specification is the binding constraint on detection.
- [[fundamental-components-of-harness]] — concrete harness-level interventions implied: assumption validation before planning, diagnosis validation before repair, recovery budget caps, independent verification of claimed success.
- [[self-improving-agent]] — Finding 8 is a caution: once an incorrect diagnosis is committed, generating more repair attempts does not improve outcomes.
- [[agent-three-layer-model]] — findings separate cleanly into model-layer (competence, 32.8%), harness/scaffold-layer (recovery behavior, monitoring), and environment-layer (9.4%) causes.
